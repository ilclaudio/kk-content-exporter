# I18N.md

Translation workflow of KK Content Exporter. Rules for writing translatable code are in
*Internationalization* of `AGENTS/CODING_STANDARDS.md`; this file covers the files and commands.


## Files

| File | Role | Edited by hand |
|---|---|---|
| `languages/kk-content-exporter.pot` | Template with every source string (English) | No: `composer run make-pot` |
| `languages/kk-content-exporter-<locale>.po` | Translation of one locale (e.g. `it_IT`) | Yes: only the `msgstr` values and the header |
| `languages/kk-content-exporter-<locale>.mo` | Compiled translation loaded by WordPress | No: `composer run make-mo` |

Text domain and slug: `kk-content-exporter`. Header: `Text Domain: kk-content-exporter`,
`Domain Path: /languages`. WP-CLI is a Composer development dependency (`vendor/bin/wp`), so the
commands work without a global WP-CLI and without a WordPress installation.


## After adding or changing strings

1. Write the strings in English with the literal text domain and the needed `translators:` comments.
2. Run `composer run i18n`: it regenerates the `.pot` (`make-pot`), merges it into every `.po`
   (`update-po`) and compiles every `.mo` (`make-mo`).
3. Translate the new or changed (fuzzy) entries of every `.po` (at least `it_IT`), then run
   `composer run make-mo` again.
4. Check the result: `composer run test:integration` (the translation test) and the Plugins screen of
   http://kkce.local with the site language set to Italian.
5. Commit the `.pot`, `.po` and `.mo` together with the code.

`make-pot` scans the plugin root and skips `vendor`, `node_modules`, `tests`, `DEV`, `AGENTS`, `bin`
and `build`; it also extracts the plugin header fields (name, description, author).


## Adding a new language

1. Create the `.po` from the template, for example for German:
   `cp languages/kk-content-exporter.pot languages/kk-content-exporter-de_DE.po`
   (or create it with Poedit / Loco Translate from the `.pot`).
2. In the header set `Language: de_DE`, `Language-Team`, `Last-Translator` and the correct
   `Plural-Forms` of the language (see https://translate.wordpress.org/ for the WordPress values).
3. Translate the entries and run `composer run make-mo`.
4. Mention the new language in `readme.txt` (Description) and in `CHANGELOG.md`.
5. Do not ship `.l10n.php` files (generated by Loco Translate or `wp i18n make-php`): the plugin ships
   `.po` and `.mo` only, which work on every supported WordPress version.

When the plugin is published on WordPress.org, community translations come from
translate.wordpress.org as language packs and take precedence over the bundled files; the bundled
`it_IT` remains the fallback.


## JavaScript translations (when the admin gets scripts)

1. Register the script with a `kkce-` handle and `wp-i18n` as a dependency; in JavaScript use
   `__()`, `_x()`, `_n()`, `sprintf()` from `@wordpress/i18n` with the literal text domain
   `'kk-content-exporter'`.
2. After registering the script, call
   `wp_set_script_translations( 'kkce-<handle>', 'kk-content-exporter', KKCE_PLUGIN_DIR . 'languages' );`.
3. `make-pot` extracts JavaScript strings too; after translating the `.po`, generate the JSON files
   with `vendor/bin/wp i18n make-json languages --no-purge` (add a Composer script `make-json` and include
   it in `i18n` in the same change). The JSON files (`kk-content-exporter-<locale>-<md5>.json`) are
   generated: never edit them, commit them with the `.po`.
4. Add an integration test that checks the script translations are registered.
