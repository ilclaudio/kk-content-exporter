# I18N.md

Translation workflow of KK Content Exporter. Rules for writing translatable code are in
*Internationalization* of `AGENTS/CODING_STANDARDS.md`; this file covers where translations come from.


## Translations come from translate.wordpress.org

The plugin ships **no translation files** and does not load any: there is no `languages/` folder, no
`Domain Path` header and no `load_plugin_textdomain()` call. Once the plugin is published on WordPress.org,
translate.wordpress.org reads the strings from the code; when a language is translated enough, WordPress
installs its language pack in `wp-content/languages/plugins/` and loads it by itself (just-in-time loading
of the text domain `kk-content-exporter`, equal to the slug).

Decision of 2026-11-28, after the first review of WordPress.org: the bundled `it_IT` translation, the
Composer scripts that generated the translation files (WP-CLI `i18n` commands) and the tests of the bundled
translation were removed.
The last Italian translation (`.pot`, `.po`, `.mo`, JSON) is kept by the operator outside the repository,
to be imported on translate.wordpress.org after the approval. `bin/release-functions.php` refuses a package
that contains a `languages/` folder.

Text domain and slug: `kk-content-exporter`. Header: `Text Domain: kk-content-exporter`.


## After adding or changing strings

1. Write the strings in English with the literal text domain and the needed `translators:` comments.
2. Keep the terms consistent with the existing strings (the same word for the same thing): translators on
   translate.wordpress.org work from the English source.
3. No file to regenerate: translate.wordpress.org reads the new strings of every released version.


## JavaScript translations

1. Register the script with a `kkce-` handle and `wp-i18n` as a dependency; in JavaScript use
   `__()`, `_x()`, `_n()`, `sprintf()` from `@wordpress/i18n` with the literal text domain
   `'kk-content-exporter'`.
2. After registering the script, call `wp_set_script_translations( 'kkce-<handle>', 'kk-content-exporter' );`
   **without a path**: WordPress then reads the JSON translations of the language packs.
3. Add an integration test that checks the script translations are registered (handle and text domain).

Scripts with strings today: `kkce-feed-mapping` (`assets/js/feed-mapping.js`). `assets/js/feed-editor.js` has no
strings: its messages are printed by the server in the box.
